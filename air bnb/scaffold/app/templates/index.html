Q1 · Inventory Schema — Per-day rows vs Range rows,哪個快?

問題：同一個業務需求「找 Honolulu 在某 N 天內全部可訂的房」,兩種 schema 都做得到,但搜尋速度差很多。

對比兩種模型:

維度 A · Per-day rows (本系統選擇) B · Range rows (替代方案)
Schema inventory(home_id, date, status) bookings(home_id, start, end, status)
12 個月 1 個房 365 筆預先 INSERT 0 筆(空表 = 全可訂)
查「N 天全可訂」 range scan + GROUP BY HAVING COUNT (B-tree 一次 seek) NOT EXISTS overlap subquery (B-tree 結構性無能,2 欄位 range 比較)
儲存成本 高 (N 房 × 365 天) 低
怎麼測:
1. 按下方 Run comparison — 系統會跑兩種 SQL 各 N 次,給你 ms 對照
2. 如果 bookings 表太空 (寫入測試前),會自動補 50 筆假 booking 進 bookings 表,讓 range query 有東西要 overlap-check
3. 看下方對照,「贏家」會被標出來

觀察:小資料下 A 和 B 都很快,差距通常在 0.1-2ms。 資料越大,B 的 NOT EXISTS overlap 會比 A 的 range scan 慢很多倍, 因為 start_date < end AND end_date > start 是兩欄位 range 比較,B-tree 結構性不擅長。 PostgreSQL 要用 GiST + tsrange 才能加速,SQLite/MySQL 沒救。

① 跑對比:per-day vs range,看哪個 ms 比較低

怎麼讓差距明顯?
• bookings 目標筆數:range 的 NOT EXISTS 會掃 bookings 表,筆數越多越慢。Per-day 不受影響。預設 2000,差距已肉眼可見;設到 20000-50000 差距會炸開 (range 慢 10-100×)。
• 更兇的玩法:先去 Admin tab 按 Seed Large 灌 3.65M inventory rows + 10K homes,然後回來把 bookings 目標筆數設到 50000。Range 的 overlap subquery 會變得超慢。
• 自動補資料只執行一次,後續同一個 target 直接用現有 bookings。要重來按 Reset bookings (only)。

Q2 · Concurrent Booking — 兩人同時搶同一房同一日期

問題:User A 和 User B 同時點「訂 H1, 9/1–9/5」,系統怎麼確保只有一個成功?

不可違反的鐵律 (invariant):no double booking, ever。

怎麼測:
1. 上面切換 Concurrency Mode (logical / naive)
2. 選一個房 + 日期
3. 按 🏁 Race A vs B — 系統會用 Promise.all 同時發 A 跟 B 兩個 reservation
4. 看下方 User A 跟 User B 兩個結果框

logical 模式(預設,推薦):用 conditional UPDATE WHERE status='available' OR (reserved AND expired),DB 在那一刻原子地檢查 + 更新, 只有一個會拿到 affected_rows == nights → 一個成功 + 一個 rejected ✓

naive 模式(教學用,故意有破綻):先 SELECT 看是否可訂,再 UPDATE。中間有 race window。 在 PostgreSQL 裡會雙雙成功 → double booking。

⚠ 為什麼 naive race 會自動加 200ms 延遲?
SQLite 對寫入有 database-level lock,加上每個 SQL < 1ms,naive 的 race window 在實務上幾乎無法對撞 — 通常 A 跑完 commit 後 B 才開始 SELECT,B 自然看到 reserved 然後 reject,看起來跟 logical 一樣 (假象)。
所以 UI 在 naive 模式時自動帶 ?delay_ms=200,在 SELECT 跟 UPDATE 中間 sleep 200ms,模擬真實系統的網路 / 處理延遲,讓 race window 變大、對撞穩定發生。 這時候你會看到 DOUBLE BOOKING DETECTED 警告 — 兩個 booking 都成立但 inventory.holder 只記得最後一個寫入的人,另一個 booking 變成孤兒 (已付款卻訂不到房)。

logical 模式不需要 delay,因為它的 conditional UPDATE 是 atomic,即使加 delay 也不會壞。

重新測之前:按 Cancel any holds 把這個房上面所有未完成的 reservation 釋放掉。

① 切換並發控制策略

切換後,任何後續的訂房請求會用新策略。

🔓 Q2 進階 Demo:三種「解鎖機制」現場對比

同樣是「reserve 後 10 秒過期」,釋放方式有三種設計,各自的故障模式不一樣。 這個 demo 把 TTL 設成 10 秒,你可以親眼看到差別。

怎麼測 (3 個 mode 都跑一遍):
1. 上方按 ① Set TTL = 10s(只設一次)
2. 切 mode → 按 A reserves 10s hold
3. 立刻按 B tries same dates 看當下行為
4. 等 10 秒之後再按一次 B 看「解鎖後」的行為

三種 mode 的預期差異:
🔒 pessimistic:A 的 reserve 自己會 hang 10 秒。期間 B 的 reserve 也會 hang(被 process-wide lock 擋)。10 秒後 A 跟 B 都返回 — 但 B 必失敗(A 已經佔住房)。整個系統等於停 10 秒。
⏳ cron:A 立即返回。B 立刻試 → reject。等 10 秒過 TTL,B 立刻試 → 仍 reject (cron 還沒跑)。等到 cron 跑過後再試 → 成功。可以按 Disable cron 模擬 cron 掛掉,B 永遠 reject。
🟢 logical (正解):A 立即返回。B 立刻試 → reject。過 10 秒立刻試 → 成功(下一個 booking 自己 take over,不靠 cron)。

Q3 · Index Strategy — 用什麼 index 讓 search 跑得快?

問題:Search query 是 WHERE city=? AND date BETWEEN ? AND ? AND status='available', 資料量 365 天 × 10K 房 = 3.65M rows,SLA 要求 < 500ms。怎麼建 index?

5 種策略可切換,每種都會即時 DROP 舊 index + CREATE 新 index,然後跑 EXPLAIN / Search / Bench 看差別。

怎麼測 (3 個工具,各有用途):

Tool 1: Single search — 跑一次 query,看 ms。最直接但小資料下差距小。
Tool 2: EXPLAIN — 看 DB 真的有沒有用上 index。這是最可信的判斷方法。
  SCAN = 全表掃描,壞 ❌
  SEARCH ... USING INDEX = 用上 index,好 ✓
  SEARCH ... USING COVERING INDEX = 用上 index + 不回主表,最好 ✓✓
Tool 3: Benchmark — 自動切過所有 5 種策略各跑 N 次,給你對照表。

5 種策略一覽:
• none: 不建 index → SCAN (全表掃)
• simple: 只對 city 建 → 用得上但只切第一刀
• compound: (city, date, status) → 經典三層 seek,推薦預設
• covering: (city, date, status, home_id) → 連回主表都免了
• partial: (city, date, home_id) WHERE status='available' → 只服務 99% 的 query,index 體積砍半

⚠ 想看真實差距:去 Admin tab 按 Seed Large 生 3.65M rows。預設的 1.5K rows 全部都很快 (1-3ms), 差距藏在 EXPLAIN 而非 ms。

① 切換 Index Strategy (6 種)

5 種策略的進階關係:
• covering = compound + 把 home_id 塞進 index → 不回表
• partial = 末尾加 WHERE status='available' → 只 50% rows 進 index,但 SELECT home_id 仍要回表
• 🔥 killer = partial + 在 index 裡多塞 home_id → 體積最小、寫入最便宜、不回表 = production 真實會用的招
切換時會 DROP 舊 index + CREATE 新 index + dispose 連線池。

② Tool 1+2: 跑單次 Search 看 ms,然後 EXPLAIN 看 query plan

③ Tool 3: Benchmark — 自動跑過所有 5 種策略

Q4 · State Machine + Idempotency — 為什麼要 reserved → paid → booked 三段?

問題:訂房經過「使用者點訂 → 跳付款頁 → Stripe 扣款 → webhook 通知」, 中間有跨公司、跨網路、跨時間的不確定性。怎麼設計狀態才能容錯?

這個 tab 把每個狀態轉移做成一個按鈕,你會看到 paid 跟 booked 是兩個獨立的 step,可以觀察到中間狀態。

怎麼測 (照著按 1-2-3-↺):

① Reserve → 狀態變 reserved,inventory 鎖 10 分鐘 (TTL),User 可以去輸入卡號
② Confirm Pay → 模擬 Stripe webhook 到 → 狀態變 paid。 注意 inventory 還是 reserved! (按 👀 Peek inventory 確認)。 這代表「我承認 Stripe 那邊收到錢了,但我家的工還沒做完」
③ Finalize → 自家 atomic transaction,inventory 才真的變 booked,booking 也變 booked
↺ Replay → 用同一個 idempotency key 再發一次 confirm,看看會不會重複扣款

為什麼 paid 和 booked 不能合一步?
因為跨系統 (你 vs Stripe) 沒有真正的 atomic。如果合一步:
1. Stripe 已扣款 → 你的 transaction commit 失敗 → 你不知道,Stripe 也不知道你不知道
2. Stripe retry webhook → 你又執行一次 → 重複處理
拆成兩步後:paid 是 checkpoint,即使 finalize 失敗,cron 可以掃「paid 但未 booked」重做。

為什麼要 idempotency?
Stripe 文件白紙黑字寫:webhook may be delivered multiple times。 重複的 webhook 必須當設計需求處理,不是 edge case。 打開 idempotency on,replay 會直接回上次結果 (idempotent_replay=true); 關掉 off,replay 會嘗試重複處理 (但 conditional UPDATE 仍會擋,只是不優雅)。

Q5 · Caching — 為什麼 Home detail 該 cache,Search results 不該?

問題:10M DAU ≈ 400K QPS,DB 撐不住,必須 cache。但 cache 什麼?

正解:cache home detail(房源資料變動低、key 簡單),絕對不要 cache search results(key 組合爆炸、invalidation 不可能)。 這個 tab 讓你親眼看到 home detail 的 cache hit/miss ms 差距。

怎麼測:

Step 1: cache on 模式 (預設)
1. 選一個房 → 按 GET (1 call) → 看到 CACHE MISS,ms 約 5-10
2. 再按一次同一個房 → 看到 CACHE HIT,ms 約 0.01-0.05
3. 通常會看到 100×–500× 加速 ⚡
4. 按 GET × 10 連發 10 次,觀察 hit rate

Step 2: cache off 模式
切到 off → 重複上面動作 → 每次都是 MISS,ms 都一樣慢

Step 3: 觀察 cache stats
下方 stats 顯示 size / hits / misses / hit rate,對照看效果

核心心法 (cache 4 維度判斷):
Home detailSearch results
變動頻率極低 ✓每筆訂房都變 ✗
Key 形狀home:{id} ✓city × dates × pageSize × page × filters 爆炸 ✗
Stale 後果「地址舊 1 小時」小事 ✓「以為可訂訂下被擋」災難 ✗
Invalidationdelete 1 個 key ✓不可能列舉 ✗

4 個維度全過才該 cache。Home detail 完美,search results 全炸。

關掉時 cache 會被清空。

③ 🏁 一鍵對比:Cache on vs off (各 100 次同房 GET)

單次 GET 的 ms 差距小看不出來,跑 100 次累積差距就很明顯。 按下後系統會: (a) 切到 cache on → clear cache → 跑 100 次 (1 miss + 99 hits) → (b) 切到 cache off → 跑 100 次 (100 misses) → (c) 還原原本的 cache 設定。 通常會看到 cache on 比 off 快 50-200 倍。
